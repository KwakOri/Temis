# R2 이미지 프록시 반복 호출 보안 검토

검토일: 2026-10-04

## 결론과 범위

현재 코드에는 외부 익명 사용자가 이미지 프록시를 직접 반복 호출해 전송량,
R2 읽기 요청과 함수 메모리를 소진시키는 경로가 있다. 일반 다운로드에서
프록시가 거의 사용되지 않는다는 사실은 이 공격 경로의 보호 장치가 아니다.
여기서 확인한 위험은 서비스 거부/비용 소진이며, 이 경로에서 서버 코드 실행이나
DB 변조가 가능하다는 증거를 발견한 것은 아니다. 앱 전체의 침입 가능성 검토도 아니다.

범위는 `/api/template-studio/assets/image`와 그 R2 읽기 helper에 한정한다.
일반 로딩, 우발적 CORS 실패, 이미지 품질 문제는 제외한다. 운영 부하 테스트,
원격 DB/R2 변경, 앱 코드 수정은 실행하지 않았다. Vercel에 별도로 설정된 WAF,
차단 규칙과 사용량 정책은 확인하지 않았으므로 실제 운영 방어 수준은 미확정이다.

## High

### R2-ABUSE-001: 익명 사용자의 반복 호출을 제한하지 않음

- 위치: `src/app/api/template-studio/assets/image/route.ts:40`의 `GET`.
- 근거: URL 검증 뒤 곧바로 R2를 읽는다. 서버 인증, 이용 권한, 호출 제한이 없다.
  기존 로컬 검증에서 쿠키 없는 단일 요청이 `200`과 이미지 147,689바이트를 반환했다.
- 영향: 공개된 이미지 URL을 아는 공격자는 실제 시간표 화면이나 PNG 생성 과정 없이
  프록시를 호출해 R2 읽기/함수 실행/이미지 전송을 반복시킬 수 있다.
- 증폭 요인: 같은 파일도 요청마다 S3 `GetObjectCommand`를 실행한다.
  응답의 `private, max-age=300`은 사용자 간 CDN 공유 캐시가 아니며,
  공격용 클라이언트가 브라우저 캐시를 따를 의무도 없다.
- 수정 방향: 비공개 이미지에는 기존 서버 인증과 템플릿 이용 권한을 적용한다.
  기존 공개 썸네일의 익명 이용은 공개 허용 목록으로 구분한다. 계정/IP 기준
  공유 저장소 기반 호출 제한과 Vercel WAF의 해당 경로 제한을 함께 적용한다.
- 완화/확인 사항: 기존 프론트엔드 `Map` 기반 rate limiter는 이 API를 보호하지 않는다.
  서버리스 인스턴스마다 독립적인 메모리 카운터만 추가하는 것도 충분하지 않다.
  운영 WAF 규칙이 있다면 위험도와 실제 허용 요청량을 재평가해야 한다.

### R2-ABUSE-002: 파일 크기와 종류를 읽기 전에 제한하지 않음

- 위치: `src/app/api/template-studio/assets/image/route.ts:58`, `src/lib/r2.ts:387`.
- 근거: `downloadFileFromR2(objectKey)`에 `maxBytes`를 전달하지 않는다.
  helper는 데이터를 끝까지 읽어 `Buffer.concat(chunks)`를 호출하며,
  API는 전체 읽기가 끝난 뒤에야 `image/` MIME을 검사한다.
- 영향: 공격자는 읽을 수 있는 큰 객체의 키를 아는 경우 대용량 파일 읽기를
  반복시켜 메모리와 실행 시간을 소진시킬 수 있다. 이미지가 아닌 파일도
  최종 응답은 거부되지만 전체 파일을 읽는 비용은 이미 발생한다.
- 확인된 규모: 복원 로컬 DB의 등록 이미지 최대 크기는 23,215,190바이트다.
  운영 메모리 고갈이나 실제 동시 요청 실패를 재현한 것은 아니다.
- 수정 방향: 등록 에셋/용도 허용 목록을 먼저 확인하고, upstream의 타입/크기를
  본문 읽기 전에 검사한다. 실제 수신 바이트에도 상한을 적용하며 제한 초과나
  시간 초과에는 읽기를 취소한다. Vercel 응답 제한을 넘는 기존 이미지를
  지원할 방법 없이 일괄 차단하는 변경은 정상 다운로드를 깨뜨릴 수 있다.
- 완화/확인 사항: MIME 사전 검증만으로는 대형 이미지 공격을 막지 못한다.
  파일 크기 제한만으로도 작은 파일의 반복 요청은 막지 못하므로 001과 함께 보완한다.

## 기존 방어와 한계

- 이미지 URL의 origin을 설정된 R2 origin과 비교하고 고정 S3 endpoint로 읽는다.
  따라서 이 코드는 외부 임의 사이트를 읽는 범용 HTTP 프록시 형태는 아니다.
  그러나 이는 이미지 대상 제한이지 호출자 인증/호출 제한이 아니다.
- R2 CORS는 브라우저의 교차 출처 접근 규칙이다. 서버에서 보내는 직접 API 요청을
  인증하거나 반복 호출을 제한하지 않는다. Origin/Referer 검사만 추가해도
  서버형 공격 클라이언트에 대한 충분한 방어가 되지 않는다.
- Vercel 4.5MB 응답 제한 때문에 큰 응답이 실패하더라도, 그 전에 발생한 R2 읽기와
  메모리 사용까지 차단되는 것은 아니다.

## 우선순위

1. 운영 WAF의 프록시 경로별 제한/차단 현황 확인 및 필요 시 edge 제한 설정.
2. 기존 공개/비공개 계약에 맞춘 인증·권한과 계정/IP별 서버 호출 제한.
3. 등록 에셋 허용 목록, 읽기 전/실제 읽기 중 크기 제한과 upstream 취소.
4. 프록시 호출 수·전송 바이트·차단 수 모니터링 및 이상 사용량 경보.

이 위험만을 이유로 Cloudflare 이전이 필수인 것은 아니다. 이전만 하면 공격 대상이
옮겨질 뿐이므로, 현재 프록시를 유지하거나 이전하더라도 위 방어는 필요하다.
