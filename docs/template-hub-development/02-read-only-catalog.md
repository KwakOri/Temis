# 02. 읽기 전용 통합 목록

상태: 완료 (2026-07-16)  
선행 단계: 01. 독립 경계와 데이터 계약

## 1. 목표

Legacy와 Studio 템플릿을 한 목록에서 검색·필터·페이지 이동할 수 있는 읽기 전용
Hub를 완성한다.

이 단계에서는 판매 유형 변경, 판매 시작·중지, 삭제 같은 mutation을 제공하지
않는다. 기존 화면과 안전하게 비교할 수 있는 조회 기준을 먼저 만든다.

## 2. 데이터 조회 범위

`templates`를 루트로 다음 관계를 조회한다.

```text
templates
├── shop_templates
│   └── template_plans
└── template_artists
    └── artists
```

목록에 필요한 최소 컬럼만 명시적으로 select한다. `*` 조인으로 응답 크기를
불필요하게 키우지 않는다.

로열티 상세 판정은 03단계에서 추가한다. 02단계에서는 작가 연결과 plan 존재
여부까지만 표시하고 `saleReadiness`는 임시로 구성하거나 미판정 상태를 명확히
표시한다.

## 3. 검색·필터·정렬

### 검색

- 이름과 설명 대상
- 서버 검색
- 클라이언트 입력은 debounce
- 페이지 offset은 검색어 변경 시 0으로 초기화

### 필터

- 엔진: 전체 / Legacy / Studio
- 게시: 전체 / 초안 / 게시됨 / 보관됨
- 판매 유형: 전체 / 일반 판매 / 맞춤 제작
- 상품: 전체 / 미구성 / 구성됨
- 판매: 전체 / 판매 중 / 판매 대기

03단계 완료 후 판매 필터에 `판매 준비`, `판매 불가`를 추가한다.

### 정렬

- 기본: `updated_at DESC`
- 같은 시간은 `id`를 보조 기준으로 사용해 페이지 결과를 안정화한다.

## 4. 목록 UI

데스크톱 테이블과 모바일 카드에서 같은 정보를 제공한다.

필수 표시:

- 템플릿 이름·설명·ID
- Legacy/Studio 배지
- draft/published/archived 배지
- 일반 판매/맞춤 제작 배지
- 상품 구성 여부
- plan 존재 여부
- 대표 작가 또는 작가 수
- 판매 중/대기 상태
- 마지막 업데이트

행 액션은 이 단계에서 비활성 또는 조회용 링크만 제공한다. 운영 mutation은
04단계에서 추가한다.

## 5. 상태 처리

- 초기 loading skeleton
- 페이지 이동 중 기존 목록 유지
- 오류 메시지와 재시도
- 검색 결과 없음
- 전체 데이터 없음
- 관계 데이터 일부가 없는 행도 목록 전체를 깨뜨리지 않음

`shop_templates`나 `template_plans`가 없는 것은 오류가 아니라 정상적인 미구성
상태다.

## 6. 성능 기준

- 기본 20개 단위 서버 페이지네이션
- count query와 목록 query에 동일한 필터 적용
- 관계 데이터로 인한 템플릿 중복 행 제거
- 클라이언트에서 전체 데이터를 받은 뒤 필터링하지 않음
- query key에 모든 서버 필터 포함

## 7. 기존 화면 대조

동일 필터 기준으로 다음을 비교한다.

- 전체 템플릿 수
- Legacy/Studio 수
- 일반 판매/맞춤 제작 수
- 상품 구성 수
- 판매 중 수
- 표본 템플릿의 상태·작가·상품 ID

차이가 있다면 신규 Hub 로직을 고치며 기존 탭의 코드는 수정하지 않는다.

## 8. 검증

### 자동 검증

- query parameter validation
- 검색 escape 처리
- 페이지 경계: 첫 페이지, 마지막 페이지, 빈 페이지
- 관계 없음/복수 관계 데이터 정규화
- camelCase 응답 계약
- 타입 검사와 변경 파일 ESLint

### 브라우저 검증

- 데스크톱과 모바일 레이아웃
- 검색 debounce
- 필터 조합
- 페이지 이동 중 화면 안정성
- 오류 재시도

- [x] 검색·필터·페이지네이션이 서버 기준으로 동작함
- [x] 기존 화면과 주요 집계 수가 일치함

## 10. 검증 결과 (2026-07-16)

### 집계 대조 (로컬 복제 DB)

| 항목 | DB 기준 | Hub | 일치 |
| --- | --- | --- | --- |
| 전체 템플릿 | 82 | 82 | O |
| Legacy | 81 | 81 | O |
| Studio | 1 | 1 | O |
| 일반 판매 | 10 | 10 | O |
| 맞춤 제작 | 72 | 72 | O |
| 상품 구성 | 10 | 10 | O |
| 판매 중 | 10 | 10 | O |

`saleStatus=unconfigured`(readiness 계산 경로)와 `hasProduct=false`(SQL 경로)가
모두 72건으로 일치해, 서로 독립적인 두 판정 경로가 교차 검증되었다.

### 브라우저 검증

로컬 dev 서버에서 실제 관리자 로그인 후 확인했다.

- 데스크톱(1440px) 테이블, 모바일(390px) 카드에서 같은 정보 표시,
  모바일 가로 스크롤 없음
- 검색 debounce: 연속 3회 입력 → Hub 요청 1회
- 필터 조합(검색 + 판매 상태)이 하나의 서버 요청으로 적용됨
- 페이지 이동 시 1/2페이지 결과가 다르고 20건씩 표시
- 필터 초기화 동작

### 알려진 사항

`saleReadiness`는 02단계 문서가 허용한 "임시 구성"이 아니라 03단계 규칙
(로열티 판정 포함)까지 서버에서 완전히 계산된 상태로 구현했다. 01단계 응답
계약에 `saleReadiness`가 포함되어 있어 임시값을 넣으면 오히려 계약이 흔들리기
때문이다. 다만 03단계의 나머지 산출물(조건별 단위 테스트, mutation의 동일 판정
재사용)은 아직 없다.

로컬 판매 중 10건이 모두 `ready=true`로 평가되어, Hub가 기존 판매 API보다 조건을
하나(plan 존재) 더 요구함에도 실제 운영 데이터와 모순되지 않음을 확인했다.
